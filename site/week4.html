The brief, and what shipped.

The Week 4 skill booster: design your own drone, pick a flight controller and sensors off the internet, draw the wiring, and think about communication protocols and compatibility.

  1. Design

    Pick the parts

    Design your own drone! Pick out a flight controller and some sensors off the internet.

    • The club's Cube Orange+ with a Here4 RTK GPS, Jetson Orin Nano, SIYI gimbal, ExpressLRS, RFD900x and a TFmini-S, on a Holybro X500 V2.
    • A researched catalog: every figure has a source, and everything a vendor does not publish is marked as an estimate with the reasoning.
    • A propulsion model calibrated to Holybro's own flight time and payload claims.
  2. Wiring

    Draw the model

    Draw a model of what the wiring setup looks like to connect everything together!

    • A generated diagram and a pin by pin harness: TX crossed to RX, flow control, who powers what.
    • It catches the TFmini-S cable: the sensor's pin order is the reverse of the Cube's.
  3. Protocols

    Ensure compatibility

    Think about communication protocols and ensure compatibility.

    • {{STAT:w4_rules}} rules: logic levels, baud rates, receive DMA, I2C addresses, CAN load and termination, 5 V budgets, regulator loads, bandwidth, firmware features, ESC and connector ratings.
    • An ArduPilot parameter file generated from the wiring and validated against 4.7.1's own metadata.
    • MAVLink, DroneCAN, CAN, RTCM, CRSF, SBUS, DShot, UART and I2C implemented from the specifications and checked against reference libraries.
  4. Beyond

    Prove it on real firmware

    Documentation is key.

    • ArduCopter 4.7.1 built from source and flown in simulation with this airframe's mass and inertia, driven only by this repo's MAVLink code.
    • The link budget predicted, then measured on the firmware; MAVLink signing set up and verified.
    • The PID slides as a simulator you can tune, next to ArduPilot's real response.

What each protocol puts on the wire.

Real captures from this week's encoders. UART frames every byte with a start and stop bit; SBUS inverts it; DShot encodes each bit as a pulse width; CAN inserts a stuff bit after five equal bits (highlighted) so every node stays in step.

{{STAT:w4_mavlink}} of {{STAT:w4_mavlink}}MAVLink messages in the ArduPilot dialect encode byte for byte like pymavlink, from the XML definitions, signing included.

15 DroneCAN typesparsed from the DSDL files, with signatures and multi frame transfers identical to pydronecan.

{{STAT:w4_cpp_cases}} caseswhere the C++17 port and the Python agree exactly: CRCs, SBUS, CRSF, DShot, CAN and MAVLink framing.

One RTK correction, five protocols.

An RTK base station's corrections reach the drone's GPS through RTCM, MAVLink, a 915 MHz radio, UART, DroneCAN and CAN. Each hop is encoded with this week's code and decoded again.
